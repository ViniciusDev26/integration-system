# 0012. Always-dark theme via Tailwind v4 tokens

- Status: Accepted
- Date: 2026-09-06

## Context

The app's frontend was requested to become a modern, Spotify-like experience.
Visually, the existing app only followed OS `prefers-color-scheme` (a plain
media query in `index.css`), with hardcoded hex colors (`#1db954`, `#0d1117`,
`gray-500/…`) repeated ad hoc across `Player.tsx`, `Layout.tsx`, and the page
components — no single source of truth for the palette, and no deliberate
dark identity (Spotify itself defaults to dark).

Adopting the real shadcn CLI (ADR 0015) to add new primitives (`avatar`,
`dropdown-menu`, `card`, etc.) brought its own semantic color-token system
(`--background`, `--foreground`, `--primary`, `--card`, …) plus a light/dark
`.dark`-class-toggle scaffold generated by `shadcn init`'s default preset —
none of which this app needs, since it has no light theme to preserve and no
requirement for a theme switch.

## Decision

- Adopt a **single, always-dark palette** expressed as CSS custom properties
  in a Tailwind v4 `@theme`/`:root` block in `src/index.css`, using the
  shadcn semantic token names (`--background: #121212`, `--card: #181818`,
  `--primary: #1db954` — the app's existing accent green — `--muted`,
  `--border`, etc.) so every generated shadcn component (and every
  hand-written one) draws from the same source of truth via `bg-background`,
  `bg-card`, `text-muted-foreground`, `bg-primary`, and so on.
- Deleted the generated light-mode `:root` values and the `.dark { … }`
  variable-override block entirely — there is only one set of values, so a
  class-based swap has nothing to toggle.
- `<html class="dark">` is set permanently in `index.html`. This keeps any
  `dark:`-prefixed utility refinements baked into generated shadcn/Radix
  component source (e.g. `dark:bg-input/30`) active, without introducing a
  toggle — `@custom-variant dark (&:is(.dark *))` (from `shadcn/tailwind.css`)
  just needs an ancestor with the `dark` class, and now it always has one.
- Dropped the OS-`prefers-color-scheme` media query and the app's previous
  ad hoc custom tokens (`--color-app-bg`, `--color-surface`, …) in favor of
  this single semantic set, so there is exactly one palette to reason about.

## Consequences

- One file (`index.css`) controls the entire palette; no more scattered
  hardcoded hex values in components (verified: `Player.tsx`, `slider.tsx`,
  and all page components now reference tokens, not literals).
- No light mode exists. If one is ever wanted, the token structure doesn't
  block it (swap values under a real `.dark`/`.light` class pair), but that
  is out of scope here and not built.
- Matches Spotify's own default (dark), which was the explicit ask.

## Alternatives considered

- **Keep the OS-preference light/dark split** and just retint both palettes:
  rejected — doubles the theming surface (a light palette would need to be
  designed and QA'd) for a feature nobody asked for; every existing hardcoded
  color in the app was already dark-leaning.
- **Keep shadcn's generated light/dark toggle scaffold** (`.dark` class swap
  with two full variable sets): rejected for the same reason — no toggle UI
  exists or was requested, so a second palette would be dead weight.
